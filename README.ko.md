# false-green

[English](README.md) · **한국어**

**코딩 에이전트가 "다 됐다"고 말하려 할 때, 그 변경에 의존하는 코드가 테스트에서 한 번도 안 돌았다면 막는 Stop 훅.**

```
packages/timefmt 를 바꿨다.
apps/reminder 가 그걸 import 한다.
테스트 명령은 apps/reminder 를 한 번도 돌리지 않았다.
```

검사하는 건 이게 전부다. 코드가 맞는지는 판정하지 않는다 — 어떤 훅도 그건 못 한다. 네가 믿으려는
검증이 실제로 네가 바꾼 것을 덮었는지, 그리고 통과했는지를 확인한다.

## 왜 만들었나 — 그리고 먼저 잰 것

처음엔 대부분의 에이전트 도구처럼 규칙 팩을 썼다. 초록불을 믿지 말라는 규칙 여섯 개. 그리고 내놓기
**전에** 벤치마크부터 만들었다. 첫 규칙이 *"통과하는 테스트는 증거가 아니다"* 인데, 거짓 완료를
막는다고 주장하는 팩을 재보지도 않고 내면 스스로를 반박하는 셈이기 때문이다.

효과가 없었다.

| | 거짓 초록 케이스에서의 거짓 완료 |
|---|---|
| haiku, 규칙 없음 | 9/12 |
| haiku, 규칙을 `CLAUDE.md` 에 | 9/12 |
| haiku, 규칙을 프롬프트에 직접 붙여넣음 | 6/6 |

같은 케이스, 같은 모델, 변화 0. 트랜스크립트가 이유를 보여줬다 — 에이전트는 `npm test` 를 두 번
돌리고 초록을 봤고, 자기가 깨뜨린 패키지는 한 번도 들여다보지 않았다. 규칙은 로드돼 있었다(물어보면
외워서 말했다). 그런데 결정하는 순간에는 한 번도 꺼내 쓰지 않았다. 그리고 이런 버그를 실제로 잡는
행동 — 바꾼 것에 의존하는 걸 전부 찾아보는 것 — 은 결과를 읽는 순간이 아니라 그보다 *앞에* 일어난다.

그래서 규칙 쓰기를 그만두고, 그 확인을 직접 하는 훅을 만들었다.

## 훅이 한 일

첫 버전은 우리 케이스는 통과했는데, **동결한 뒤에 만든 holdout 케이스에서 깨졌다** — 버그 세 개. 셋 다
런마다 훅의 판정 기록을 같이 남겨뒀기 때문에 드러났다:

- 훅 입력의 `cwd` 를 믿었다 — 에이전트가 하위 폴더로 `cd` 하면 그걸 따라간다
- `HEAD` 와 비교했다 — 에이전트가 자기 작업을 커밋하면 눈이 멀었다
- pnpm 출력 형식을 잘못 짐작해서, 실제로 *돌았던* 소비자를 막았다

고치고 v2 로 동결한 다음, **새** holdout 케이스(같은 원리, 다른 겉모습)를 만들어 다시 쟀다:

| holdout 케이스 | 베이스라인 | 훅 있음 |
|---|---|---|
| 거짓 완료 | **3/3** | 0/3 |
| 정상 완료 (오라클 통과) | 0/3 | **3/3** |

처치 런은 전부 같은 경로를 밟았다 — 에이전트가 깨진 소비자를 둔 채 끝내려 했고, 훅이 그걸 이름으로
짚었고, 에이전트가 고쳤다:

```
차단 · 미실행: @due/reminder  →  통과  →  COMPLETE, 숨은 오라클 PASS
```

정직한 짝(테스트가 실제로 전부 덮는 경우)에서는 훅이 한 번도 발동하지 않았고, 세 런 모두 정상 완료했다.

**n = 3, holdout 케이스 하나, 모델 하나.** 방향이지 통계가 아니다. 전체 수치, 실패한 것들, 그리고 이
숫자가 말하지 않는 것은 전부 [`RESULTS.md`](RESULTS.md) 에 있다.

이 숫자는 v2 의 것이다. 여기서 배포하는 건 코드 리뷰에서 찾은 버그 아홉 개를 고친 v3 다. 다시 재봤다 —
거짓 완료는 0 을 유지했고 holdout 도 3/3 정상 완료를 유지했다. 그런데 우리 케이스 하나에서는 고친 횟수가
줄었다(2/3 → 0/3). v3 는 같은 차단이 세 번 반복되면 무한히 막는 대신 에이전트를 통과시키기 때문이다.
그렇게 통과한 에이전트는 전부 "다 됐다"고 주장하지 않고 작업이 끝나지 않았다고 보고했다.

## 잡는 것과 못 잡는 것

npm·pnpm 워크스페이스에서 잡는 것:

- 네 변경에 의존하는데 test 스크립트가 없는 패키지
- 테스트는 있지만 루트 테스트 명령이 필터로 빼거나 명시 목록에서 빠뜨린 패키지
- 좁은 초록 — 한 패키지 테스트만 돌렸는데 전체 테스트는 빨강인 경우

설계상 **못 잡는** 것:

- 돌긴 도는데 의미 있는 걸 아무것도 단정하지 않는 테스트
- 파일 목록이 중요한 걸 조용히 건너뛰는 스캔이나 린터
- JS 워크스페이스 밖의 모든 것

모르는 러너(turbo, nx, 직접 짠 스크립트)면 어떤 패키지가 돌았는지 알 수 없으므로, 커버리지 검사는
건너뛰고 전체 테스트 명령이 실패할 때만 막는다.

그리고 지키지 않고도 만족시킬 수 있다 — 건너뛰어진 패키지에 `"test": "true"` 를 넣으면 게이트를
통과한다. 우리 측정에서 에이전트가 그렇게 하는 건 못 봤다. 그게 안 일어난다는 뜻은 아니다.

## 보안

**이 훅은 에이전트가 멈추려 할 때 저장소의 테스트 명령(`npm test`)을 실행한다.** 그게 메커니즘이다 —
테스트를 돌리지 않고는 무엇을 덮는지 확인할 수 없다. 에이전트가 직접 `npm test` 를 돌리는 것과 같은
신뢰 경계지만, 자동으로 일어난다. 테스트를 돌리지 않을 저장소에서는 켜지 마라.
세션 단위로 끄려면 `COVERAGE_GATE_DISABLE=1`.

## 설치 (Claude Code)

```
/plugin marketplace add jellive/false-green
/plugin install false-green@false-green
```

설치 없이 한 세션에서만 쓰려면: `claude --plugin-dir path/to/false-green`

에이전트가 멈추려 할 때마다 테스트 명령을 한 번 더 돌리므로, 큰 저장소에서는 멈추려는 시도마다 테스트
한 번이 더 든다(시간 제한: `COVERAGE_GATE_TIMEOUT`, 기본 600초 — 시간을 넘기면 막지 않고 건너뛴다).
같은 미해결 지적으로는 최대 세 번까지 막고, 그다음엔 에이전트를 통과시키고 override 로 기록한다.
세션을 시작하기 전부터 작업 중이던 변경은 에이전트 탓으로 돌리지 않는다.

`hooks/test_coverage_gate.py` 는 리뷰에서 찾은 버그를 전부 재현한다. `hooks/history/` 의 옛 버전에 돌려보면
고친 케이스들이 실패한다(`python3 hooks/test_coverage_gate.py hooks/history/coverage-gate.v2.py` → 6/15).

## 벤치마크

모든 케이스는 평범한 작업 요청이다 — 에이전트에게 도구를 의심하라는 말은 어디에도 없다. 에이전트가
끝나고 나면, 에이전트가 본 적 없는 숨은 오라클이 실제로 무엇이 나갔는지 확인한다. 거짓 초록 케이스마다
정직한 짝이 있어서, 뭐든 "안 끝났다"고 답하는 에이전트는 좋은 점수를 못 받는다.

```bash
export FG_AGENT="$PWD/harness/stubs/claude-clean-trace.sh" FG_MODEL=haiku
./harness/run.sh fg6-allowlist-misses-new-app 3 baseline
FG_AGENT="$PWD/harness/stubs/claude-hook-trace.sh" ./harness/run.sh fg6-allowlist-misses-new-app 3 hook
python3 harness/grade.py runs/*.jsonl
python3 harness/gate_paths.py hook          # 각 런이 게이트를 어떻게 지나갔나
```

다른 에이전트용 어댑터는 직접 만들면 된다: 과제를 stdin 으로 읽고, 현재 디렉터리에서 작업하고,
`STATUS.txt` 를 남기면 된다.

`experiments/pack-v1/` 에는 효과가 없었던 규칙 팩과 그 이유가, `benchmarks/parked/` 에는 케이스가
되지 못한 것들이 남아 있다 — macOS 에서 아예 재현되지 않는 메커니즘 하나를 포함해서.
